# Période GPT : actes de Claude

Texte repris de `CLAUDE.md` à `d5cdb51` (sous-section « ChatGPT (Codex) et la branche `main-GPT` » et branches de période de « Git et GitHub »), à l'identique hors renvois internes adaptés et mention caduque « à reporter dans l'ADR » corrigée (GIT-10h) ; déplacé par l'ADR 0017 ; `CLAUDE.md` en garde le résumé.

## Branches de Claude propres à la période

Autres branches de Claude hors de sa branche de travail, toutes bornées à la période GPT (décision du 29/09/2026, qui étend l'annotation du 28/09 de l'ADR 0007, reportée dans l'ADR 0007, annotation du 29 septembre 2026) : `claude/ouverture-main-gpt-<date>`, la branche de résolution d'un conflit d'intégration, `claude/regeneration-gpt-<issue>` et `claude/audit-main-gpt-<date>` (ci-dessous).

## Règles

ChatGPT (Codex Cloud, `@codex` sur les PR, ChatGPT avec le connecteur GitHub, ou Codex en local) intervient **par périodes** ; Claude reste le contributeur principal. Ses règles sont dans `AGENTS.md` et `.codex/` (fiches de rôle, procédures, script de setup) ; la décision et ses raisons dans `docs/adr/0012-…`. Ce qui concerne Claude :

- **Périmètres séparés.** Les méthodes des deux contributeurs diffèrent et ne doivent pas déteindre l'une sur l'autre : une session de Claude, ses agents et ses workflows ne lisent ni n'appliquent `AGENTS.md`, `.codex/`, `docs/feuille-de-route-gpt.md`, ni les livrables des rôles GPT (commentaires de PR, corps des PR `gpt/…`), **sauf pendant un audit ordonné, pour ouvrir ou fermer une période, ou pour une fermeture M30 déléguée** (ci-dessous) ; réciproquement, `AGENTS.md` interdit à GPT de lire `.claude/` et les sections de processus de `CLAUDE.md`. Claude ne modifie `AGENTS.md` et `.codex/` que sur instruction du mainteneur (domaine `claude:`).
- **`main-GPT`** est le `main` parallèle de GPT ; elle reçoit les PR de ses branches de travail (fusionnées par le mainteneur) et est **supprimée après sa fusion dans `main`**. **Ouverture d'une période, par Claude sur ordre du mainteneur**, une fois le lot fixé par le mainteneur dans la fiche « période GPT » de la feuille de route (proposé par `architect`) : créer `main-GPT` depuis `main` (à défaut, si le proxy ou le ruleset refuse, le mainteneur la crée depuis l'interface) ; sur une branche `claude/ouverture-main-gpt-<date>` partie de `main-GPT`, un commit `docs:` unique qui **copie dans `docs/feuille-de-route-gpt.md` la `docs/feuille-de-route.md` de la tête de la branche de travail de Claude** (SHA cité dans le message), PR vers `main-GPT` (fusionnée par le mainteneur) ; puis PR brouillon `main-GPT` → `main` (la PR de période). **Intégration de `main`** : le mainteneur, par « Update branch » de la PR de période ou, si le ruleset de `main-GPT` le refuse, par une PR `main` → `main-GPT` ouverte par Claude ; en cas de conflit, Claude le résout sur une branche partie de `main-GPT`, PR vers `main-GPT`. **Fermeture M30 déléguée par GPT** (Codex Cloud ne reçoit pas l'artefact et ne pousse pas ; décision du 29/09/2026) : sur ordre du mainteneur, Claude fait les vérifications (a′)-(c) et le commit unique code + `.rds` sur une branche `claude/regeneration-gpt-<issue>` partie de la tête de la branche de travail GPT, avec une PR vers celle-ci, selon la skill `verifier-reproductibilite`. Hors de ces actes et de l'audit, une session de Claude n'écrit jamais sur `main-GPT` ni sur une branche `gpt/…`.
- **Audit de `main-GPT`, lancé par le mainteneur seul** (jamais d'office, ni par un workflow ni par un agent) : skill **`audit-main-gpt`**. Il porte sur le diff `main...main-GPT`, les issues que GPT déclare résolues et celles qu'il a créées (liste dans la PR de période, libellé `gpt` ; tout rôle GPT peut en créer après confirmation du mainteneur, et **chacune est revue par l'agent de Claude que son objet désigne**, `actuary` pour une issue actuarielle, `regulatory` pour une issue réglementaire, etc.), avec les agents que désignent les déclencheurs de `CLAUDE.md` (« Sous-agents »), `architect` et `actuary` compris. Le travail de GPT est fait à distance, par rôles séparés dans le temps et relayés par le mainteneur : le risque d'erreur y est nettement plus élevé, et l'audit est **plus exigeant qu'une revue finale** (aucune affirmation de GPT présumée vraie, tout remesuré ; détail dans la skill). Il vise aussi à **simplifier et optimiser** le code de GPT. Les modifications de Claude passent par une branche `claude/audit-main-gpt-<date>` créée depuis `main-GPT`, avec PR vers `main-GPT` ; elle **supprime `docs/feuille-de-route-gpt.md`** (signal, pour GPT, que la période est close ; `architect` en tire le bilan de la période, reporté dans `docs/feuille-de-route.md` sur la branche de travail de Claude après la fusion). Claude valide ensuite la PR de période ; la fusion reste au mainteneur.
- En cas de conflit de fond entre `main-GPT` et une décision déjà prise sur `main`, `main` l'emporte.

Depuis l'ADR 0017 (Q-56-12), `AGENTS.md` fait une exception bornée à l'interdiction de `.claude/` : GPT lit `.claude/rules/moteur.md`, document de fond ; le reste de `.claude/` lui reste interdit.
